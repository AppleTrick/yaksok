# 개발 여정 — 커밋 로그로 재구성한 의사결정의 흐름

> 커밋을 시간순으로 따라가며, 각 시점에 어떤 문제와 마주쳤고 왜 그 선택을 했는지 재구성한 기록이다. 결과물이 아니라 **과정**의 문서다.

## 타임라인 요약

```
1/13~15  기획·기록 (SSAFY 일일 기록 커밋)
1/16~20  프론트 PWA + FastAPI YOLO 뼈대 동시 시작
1/21~27  데이터 파이프라인 구축 (자동 라벨러, 검수 도구) + OCR 삽질 (EasyOCR→PaddleOCR)
1/28~30  분석 리포트 + 알림/FCM 기반
2/4~6    보안 강화 + SSE/FCM 하이브리드 알림 구현
2월 중순  master 정리, 배포 준비
3~5월    서킷 브레이커, Docker, Jenkins CI
6월      운영 이슈 대응 (FCM 크래시, 알림 무한발송, OCR 전환 분석, LLM→Groq)
```

## 1장. 세 갈래를 동시에 (1/16 ~ 1/20)

프론트(PWA), FastAPI(YOLO), 백엔드가 며칠 간격으로 나란히 시작됐다. 특징적인 초기 결정은 1/18 `YOLO 모델을 Nano에서 Medium(m)으로 업그레이드`.

**고민**: 실시간성을 위해선 가벼운 Nano가 유리하지만, 영양제 병은 작고 라벨이 복잡해 정확도가 부족했다.
**선택**: 속도보다 정확도. Medium 모델로 올리고, 추론은 어차피 별도 FastAPI 서버에서 도니 프론트 부담과 분리했다. 이 "AI를 별도 서버로 분리" 결정이 이후 전체 아키텍처의 축이 된다.

## 2장. 데이터가 모델을 만든다 (1/21 ~ 1/27)

이 프로젝트의 진짜 엔지니어링은 여기 있다: `데이터 수집 크롤러 및 전처리 파이프라인 구축`, `YOLO-World 기반 자동 라벨러 및 시각적 검수 도구 추가`, `DataPipeLine 구조 체계화 및 Version 3 모델 통합`.

**고민**: 영양제 탐지 모델을 만들려면 라벨링된 데이터가 필요한데, 수천 장을 손으로 라벨링할 수 없다.
**선택**: YOLO-World로 자동 라벨링 → `review_labels.py` 검수 도구로 사람이 빠르게 교정하는 Human-in-the-loop. 그리고 V2에서 컵·텀블러 오탐지가 늘자 Negative Sampling으로 대응 ([TROUBLESHOOTING #2](./TROUBLESHOOTING.md#2)). 모델을 코드로 튜닝하는 대신 데이터로 문제를 푼 것.

## 3장. OCR 삽질의 기록 (1/26 ~ 1/27)

커밋이 방황을 그대로 보여준다: `OCR 기능 구현 (EasyOCR)` → `paddleOCR 적용` → `paddleOCR 개선` → 이후 여러 전처리 커밋(CLAHE, 샤프닝, denoising, line grouping).

**고민**: 곡면 병에 인쇄된 작은 글씨를 범용 OCR이 못 읽는다.
**선택 (당시)**: EasyOCR → PaddleOCR로 갈아타고, OpenCV 전처리를 겹겹이 쌓아 정확도를 코드로 메꾸려 했다. 이 삽질의 흔적이 나중에 "관리형 API 전환이 옳았다"는 판단의 근거가 된다 ([OCR 리포트](./report/OCR_PIPELINE_TECHNICAL_REPORT.md)) — 전처리를 아무리 쌓아도 범용 모델의 한계는 남았다.

## 4장. 알림, 서비스의 심장 (1/28 ~ 2/6)

영양제 앱의 핵심 가치는 "제때 알려주는 것"이다. 알림 관련 커밋이 2주에 걸쳐 진화한다:

1. 1/20~30 기본 알림 UI, FCM 기반, 권한 배너
2. 2/6 `sse fcm 하이브리드 구현 및 버그들 fix` — **핵심 전환점**

**고민**: FCM 푸시만 쓰면 앱을 보고 있어도 시스템 알림이 떠 중복되고, SSE만 쓰면 백그라운드 사용자에게 도달하지 못한다.
**선택**: 접속 상태(SSE 연결 여부)로 채널을 분기하는 하이브리드. 즉시성(SSE)과 도달성(FCM)을 상태로 나눠 확보했다. 이후 번들링(같은 시간 여러 영양제 통합)과 무한 재발송 방지(rescheduleAfterSend)까지 더해 완성 ([알림 리포트](../notification_optimization_report.md)).

같은 시기 `FastAPI에 IoU 기반 중복 객체 탐지 제거(NMS-like)`, `ProductIngredient 중복 저장 방지` — 탐지·저장 양쪽의 중복 문제를 동시에 정리했다.

## 5장. 배포 가능한 물건으로 (3월 ~ 5월)

- 3/13 `Resilience4j 서킷 브레이커 + ThreadPoolTaskExecutor 적용` — 외부 AI 서버 호출이 실패해도 백엔드 전체가 무너지지 않도록 격리
- 3/31 `SSR window 접근 가드` — Next.js SSR에서 브라우저 전용 API 접근 크래시 방어
- 5/3 Docker 배포 설정, 5/17 Jenkins CI

**고민**: AI 서버(FastAPI)는 느리고 실패할 수 있는 외부 의존이다. 이게 백엔드를 물고 늘어지면 안 된다.
**선택**: 서킷 브레이커로 AI 호출을 격리하고 별도 스레드풀로 분리. "느리고 불안정한 것"을 시스템 경계로 감쌌다.

## 6장. 운영이 드러낸 것들 (6월)

실서비스에서 문제가 연달아 나왔고, 각각을 추적했다:

- 6/14 `Firebase 미설정 시 크래시 루프 방지` — FCM 설정 누락이 앱 전체를 죽이던 것을 방어
- 6/16 `알림 무한 재발송 방지`, `CORS 운영 도메인 누락으로 POST/PUT/DELETE 차단`
- 6/17 대규모 분석 세션: FastAPI Gemini를 공식 API로 직접 호출 전환, PNG(RGBA) 500 수정, **PaddleOCR ARM 세그폴트 발견**([TROUBLESHOOTING #1](./TROUBLESHOOTING.md#1)), 백엔드 "성분분석 안 됨"의 조용한 실패 추적 → **LLM을 Groq로 교체**([#5](./TROUBLESHOOTING.md#5))

**이 프로젝트를 관통하는 패턴**: ① AI를 별도 서버로 분리하고 시스템 경계(서킷 브레이커)로 감쌈, ② 모델 문제를 코드가 아니라 데이터로 해결(Negative Sampling), ③ 다채널(알림·OCR·LLM)을 상태/폴백으로 분기, ④ 배포 전에 끝까지 실행해 세그폴트 같은 회귀를 잡음.
