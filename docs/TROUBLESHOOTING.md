## 1. PaddleOCR을 배포했다면 서버가 통째로 죽었을 것 — ARM 세그폴트

**증상** — OCR 서버를 새 환경에 재설치하니 PP-OCRv5 모델 로드 자체가 실패: `(InvalidArgument) Type of attribute: strides is not right`.

**추적** — `requirements.txt`를 보니 버전 고정이 비대칭이었다: `paddlepaddle==3.0.0`(정확히 고정) vs `paddleocr>=2.9.0`(하한만). 처음엔 최신이던 paddleocr가 시간이 지나 3.7.0으로 드리프트됐고, 이 버전이 받는 모델이 더 새로운 PIR 포맷이라 고정된 런타임이 해석하지 못했다.

**더 깊은 추적** — 호환 조합(`paddleocr==3.1.1` + `paddlex==3.1.1` + `paddlepaddle==3.0.0`)을 역추적해 모델 *로드*는 성공시켰다. 그런데 실제 `predict()` 호출 시 **다른 지점에서 세그폴트가 발생하며 uvicorn 프로세스 전체가 죽었다.** 운영 호스트가 `docker ps`로 확인 결과 **linux/arm64**였고, PaddlePaddle ARM 추론 빌드의 PIR 경로 불안정이 원인으로 보였다.

**결정** — 버전 핀을 적용하지 않고 원복. 레거시 OCR 경로(`/ai/v1/analyze`)는 OCR 실패 시 빈 값만 반환하는 안전 상태로 유지하고, 운영은 Google Vision 경로(`/analyze2`)로. 세그폴트가 같은 프로세스의 Vision 경로까지 끌고 죽는 것을 막기 위한 선택.

**교훈** — `>=` 하한 핀은 시간이 지나면 반드시 깨진다. 그리고 "고쳤다"고 생각한 버전 조합이 로드는 통과하고 추론에서 죽을 수 있다 — **끝까지 실행해봐야 안다.** 배포 전에 이걸 발견한 것이 사고를 막았다.

## 2. 영양제 오탐지 — 데이터를 늘렸더니 오히려 늘어난 False Positive

**증상 (V2)** — 조명·각도 증강으로 데이터를 520장→1,250장으로 늘렸더니 탐지율은 올랐는데, 텀블러·컵을 영양제로 오인하는 False Positive가 늘었다.

**원인** — 학습 데이터에 "영양제가 있는 이미지"만 있었다. 모델은 "병처럼 생긴 것 = 영양제"로 학습됐고, 유사 물체를 구분할 근거가 없었다.

**수정 (V3)** — Negative Sampling: 영양제가 *없는* 이미지(COCO 등)를 학습에 포함해 "이건 영양제가 아니다"를 명시적으로 학습. + `review_labels.py` 검수 도구로 라벨 정제. 결과: mAP@50 0.814, Precision 0.921.

**교훈** — "데이터를 더 넣으면 좋아진다"는 항상 참이 아니다. 오탐지는 positive를 늘려서가 아니라 negative를 가르쳐서 잡는다.

## 3. 알림이 두 번 울린다 / 무한 재발송된다

**증상** — ① 앱을 보고 있는데 인앱 토스트와 시스템 푸시가 같이 옴. ② 발송된 알림이 매분 배치마다 계속 재발송됨.

**원인** — ① SSE와 FCM을 동시에 발송하고 있었다. ② 발송 후 `next_notify` 시각을 갱신하지 않아, `intaken=false`인 동안 매분 스케줄러가 같은 알림을 계속 발송 대상으로 집었다.

**수정** — ① 채널 우선순위 라우팅: SSE 연결됨 → SSE로만(FCM 생략), 없음 → FCM. 프론트는 화면 Visible이면 토스트만. ② `rescheduleAfterSend()`로 발송 직후 snooze 쿨다운 부여. + 프론트 동일 알림 ID 10초 중복 차단.

**교훈** — 다채널 알림은 "둘 다 보내기"가 아니라 "상태를 보고 하나만 보내기"가 정답. 반복 스케줄러는 발송 후 상태 갱신을 반드시 세트로 설계해야 한다.

<a id="4"></a>
## 4. 묶음 알림인데 첫 번째 영양제만 복용 처리됨

**증상** — "비타민C 외 2건" 묶음 알림에서 복용 버튼을 눌러도 첫 번째 품목만 복용 기록됨.

**원인** — 묶음 알림은 여러 notification ID를 담는데, 복용 처리 로직이 단일 ID만 처리하고 있었다. 토스트와 서비스 워커(백그라운드) 양쪽 모두.

**수정** — 다중 ID를 파싱해 묶인 모든 영양제에 복용 기록. 토스트와 `firebase-messaging-sw.js` 양쪽 반영. 복용 처리 메서드에 `@Transactional` 적용으로 일괄 반영 보장.

**교훈** — 번들링은 "발송"만이 아니라 "응답 처리"까지 다중 ID를 관통해야 완성된다. 발송만 묶고 처리를 안 묶으면 조용히 데이터가 누락된다.

<a id="5"></a>
## 5. "성분분석이 안 돼요" — 에러 없이 조용히 실패한 LLM 호출

**증상** — 영양제 성분 분석 결과가 항상 빈 값.

**추적** — `OcrAnalysisService.fetchAndSaveProductFromLlm()` → `LLMServiceFacade` → `OpenAILLMServiceImpl` 호출 체인을 따라가니, `.env`의 `OPENAI_API_KEY`가 비어 있어 매번 `RuntimeException("OpenAI API Key 설정 오류")` → 예외를 캐치해 빈 성분 리스트만 반환하고 있었다. **에러 로그도 사용자 오류도 없이 조용히 실패.**

**원인** — `application.yml`의 기본 API URL이 SSAFY GMS 프록시였는데, 팀원이 개인 키(`sk-...`)를 쓰려고 공식 OpenAI URL로 바꾼 상태였다. 즉 개인 OpenAI 키가 필요한데 키가 비어 있었다.

**수정** — LLM을 OpenAI에서 Groq로 교체. `groq/compound` 호출 실패 시 `qwen/qwen3.6-27b`로 자동 폴백. 두 모델 모두 curl로 200 확인 후 배포.

**교훈** — ssadagu·ijip과 동일한 패턴: **폴백이 장애를 숨긴다.** "빈 값 반환"은 안전하지만 기능이 죽은 것을 가린다. 조용한 실패는 반드시 관측(로그/모니터링)되어야 한다.

<a id="6"></a>
## 6. PNG(RGBA) 이미지 업로드 시 500 에러

**증상** — `/ai/v1/analyze2`에 투명 채널 있는 PNG를 올리면 `OSError: cannot write mode RGBA as JPEG`로 크래시.

**원인** — `vision_service.py`가 정규화 이미지를 무조건 JPEG로 저장하는데, JPEG는 알파 채널을 지원하지 않는다.

**수정** — RGBA/팔레트 이미지를 흰 배경에 합성해 RGB로 변환 후 저장. JPEG/PNG 둘 다 정상 확인.

**교훈** — 이미지 입력은 포맷·색공간이 제각각이다. 외부에서 들어오는 이미지는 처리 전 색공간 정규화가 필요하다.

## 7. 빌드가 너무 느림 — 6.56GB 빌드 컨텍스트

**증상** — FastAPI 컨테이너 재빌드가 유독 느림.

**원인** — 로컬 검증용으로 만든 `fastapi/venv/` 폴더(수 GB)가 `.dockerignore` 부재로 빌드 컨텍스트에 통째로 포함됐다.

**수정** — `venv/` 정리. (`.dockerignore` 추가 권장 — [CODE_REVIEW](./CODE_REVIEW_20260705.md) 참고)

**교훈** — 빌드가 느리면 이미지가 아니라 컨텍스트 크기를 먼저 의심. `.dockerignore`는 선택이 아니라 필수.

<a id="8"></a>
## 8. LLM/OCR 제공자 교체기 (GMS 프록시 → 공식 API)

**배경** — 초기엔 SSAFY GMS 프록시(`gms.ssafy.io`)로 OpenAI/Gemini를 호출했다. 개인 운영으로 넘어오며 프록시 키가 무효화되어, ① Gemini는 Google 공식 엔드포인트 직접 호출로(발급 키가 GMS가 아닌 AI Studio 표준 키였음), ② 백엔드 성분 정제 LLM은 OpenAI → Groq로 교체.

**교훈** — 교육/사내 프록시에 의존한 외부 API는 환경이 바뀌면 전부 끊긴다. 제공자를 설정으로 분리해두면 교체가 설정 변경으로 끝난다 (ijip·ssadagu와 동일 교훈).
