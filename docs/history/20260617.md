## 3. 버그 수정 — `/ai/v1/analyze2` PNG(RGBA) 500 에러
- `vision_service.py`의 `analyze_logic()`에서 정규화 이미지를 무조건 JPEG로
  저장하던 로직이 RGBA(투명 채널) PNG 입력 시 `OSError: cannot write mode
  RGBA as JPEG`로 크래시
- RGBA/팔레트 이미지를 흰 배경에 합성해 RGB로 변환 후 저장하도록 수정
- JPEG/PNG 둘 다 정상 동작 확인 (회귀 없음)

## 4. PaddleOCR → Google Vision API 전환 배경 분석
- YOLO+PaddleOCR 로컬 OCR 경로의 속도/정확도 문제를 git 히스토리 기반으로 분석
- `requirements.txt`의 `paddleocr>=2.9.0`(하한만 고정)이 시간이 지나며 최신
  버전(3.7.0)으로 드리프트되어 `paddlepaddle==3.0.0`과 호환되지 않는
  PIR 포맷 불일치(`strides` 어트리뷰트 에러)를 일으킨다는 점을 확인
- 호환 버전 조합(`paddleocr==3.1.1` + `paddlex==3.1.1` + `paddlepaddle==3.0.0`)을
  찾아 모델 *로드*는 성공시켰으나, 실제 추론(`predict()`) 시점에 **세그폴트로
  서버 프로세스 전체가 죽는 더 심각한 문제**를 발견
- 이 서버(운영 호스트)가 실제로 **linux/arm64**임을 `docker ps`로 확인 →
  세그폴트 위험이 추측이 아닌 실재하는 운영 리스크임을 확인
- 상세 분석은 [`../report/OCR_PIPELINE_TECHNICAL_REPORT.md`](../report/OCR_PIPELINE_TECHNICAL_REPORT.md) 참고
- **결정**: `requirements.txt`의 paddleocr 버전 핀은 적용하지 않고 원래대로
  유지 (세그폴트 회피). `/ai/v1/analyze`는 기존처럼 OCR 실패 시 빈 값만
  반환하는 안전한 상태로 둠

## 5. 운영 서버 재배포
- 안전이 확인된 변경분만 배포: `llm_service.py`, `vision_service.py`,
  `.gitignore` (`requirements.txt`는 원복 상태로 배포, paddleocr 핀 제외)
- `docker compose build yaksok-fastapi && docker compose up -d yaksok-fastapi`로
  운영 컨테이너 재빌드·재시작
- 빌드 컨텍스트가 6.56GB로 비대해 빌드가 느렸던 원인 파악 — 로컬 검증용으로
  만들었던 `fastapi/venv/` 폴더(수 GB)가 `.dockerignore` 부재로 그대로
  포함됨. 배포 후 `venv/` 폴더 삭제로 정리
- 배포 후 컨테이너 내부에서 직접 검증:
  - `GET /` → 200
  - `POST /ai/v1/analyze2` (Vision API + Gemini) → 200, 제품명 "센트룸 멀티 구미" 정확히 추출
  - `POST /ai/v1/analyze` (YOLO+OCR) → 200, 컨테이너 정상 생존 (세그폴트 없음)
- git commit/push는 진행하지 않음 — 변경분을 영구히 남기려면 별도로 커밋·푸시 필요
  (Jenkins는 `git pull origin master` 기준으로 빌드하므로 현재 변경은 로컬
  파일시스템 + 운영 컨테이너에만 반영된 상태)

## 6. 백엔드 성분분석 실패 원인 분석 — OpenAI API Key 미설정
- "성분분석이 안 된다"는 증상을 추적: `OcrAnalysisService.fetchAndSaveProductFromLlm()`
  → `LLMServiceFacade` → `OpenAILLMServiceImpl`로 이어지는 LLM 호출 체인에서
  `backend/yaksok/.env`의 `OPENAI_API_KEY`가 비어있어 매번
  `RuntimeException("OpenAI API Key 설정 오류")`가 발생, 예외를 캐치해 빈
  성분 리스트만 반환하고 있었음 (에러 없이 조용히 실패하는 형태)
- `application.yml`의 `openai.api.url` 기본값이 SSAFY GMS 프록시
  (`gms.ssafy.io/gmsapi/api.openai.com/...`)였으나, 커밋 `bbc2deb`에서 팀원이
  "개인 키(`sk-...`) 사용 시 공식 API를 호출해야 한다"며 OpenAI 공식 URL로
  변경한 이력 확인 — 즉 SSAFY GMS 키가 아닌 개인 OpenAI 키가 필요한 상태였음

## 7. 백엔드 LLM을 OpenAI → Groq로 전환
- `OpenAILLMServiceImpl.java` 삭제, `GroqLLMServiceImpl.java` 신규 작성
  - Groq의 OpenAI 호환 API(`https://api.groq.com/openai/v1/chat/completions`) 호출
  - 기본 모델 `groq/compound` 호출 실패 시 폴백 모델 `qwen/qwen3.6-27b`로
    자동 재시도하는 로직 추가
- `application.yml`: `openai.*` 설정 → `groq.*`로 교체
  (`groq.api.key`, `groq.api.url`, `groq.model.primary`, `groq.model.fallback`)
- `backend/yaksok/.env`: `OPENAI_*` → `GROQ_API_KEY`, `GROQ_API_URL`,
  `GROQ_MODEL_PRIMARY`, `GROQ_MODEL_FALLBACK`로 교체, 발급받은 Groq 키 적용
- 검증:
  - `docker compose build yaksok-back` → BUILD SUCCESSFUL
  - Groq API에 `groq/compound`, `qwen/qwen3.6-27b` 두 모델 모두 직접 curl로
    호출해 200 응답 확인 (키·모델 ID 유효성 검증)
  - `docker compose up -d yaksok-back` 재배포 → 기동 로그에서 Groq 키 로드,
    Primary/Fallback 모델 설정 정상 출력, `Started YaksokApplication` 확인
